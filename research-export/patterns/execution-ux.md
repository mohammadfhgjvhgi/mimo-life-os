# Execution UX Pattern

> Pattern synthesis (PAT-2). Evidence-based synthesis from 11 product evidence files (gemini, manus, cursor, claude-code, codex, openhands, langgraph-studio, dust, lovable, bolt, v0). No MiMo design recommendations. Every claim cites `evidence/<product>.md §<section>`.

---

## 1. Pattern Definition

**Execution UX** is the design pattern by which an AI-augmented product surfaces the *runtime experience* of an agent or long-running task — from invocation, through plan/execution/observation, to completion or interruption. It is the user-visible layer over the agent loop: `user prompt → plan → tool calls → observations → synthesis → result`. Execution UX governs what the user sees at each step, what they can interrupt, when they must approve, how progress is disclosed, and how the final artefact is rendered.

Six observable parts:

1. **Invocation surface** — the trigger: explicit prompt (Manus chat), Cmd+K (Cursor generative), `claude` CLI invocation (Claude Code), sandbox-boot on first prompt (v0).
2. **Plan checkpoint** — does the system surface a plan for human approval before execution? (Gemini Edit Plan, Manus Plan Mode, Cursor Plan Mode, Claude Code `--permission-mode plan`, Lovable Plan Mode, Bolt Plan Mode, v0 plan docs).
3. **Runtime visibility** — what does the user see as the agent runs? Live terminal output (Manus Desktop), animated graph traversal (LangGraph Studio), event-stream (OpenHands), streaming activity events (Linear), activity cards (Lovable, v0), live browser screenshots (Manus Cloud Browser, v0).
4. **Interruption / approval affordances** — Allow Once vs Always Allow (Manus Desktop), Shift+Tab to enter Plan Mode (Cursor), `--approve-for-me` (Codex), `--bg` background (Claude Code), Stop button (Lovable, Dust).
5. **Artefact rendering** — Markdown report (Gemini Deep Research, Manus), code diff (v0, Lovable), version history (Bolt), file/line metrics (v0 work details).
6. **Completion semantics** — synchronous block (Claude Code interactive), async continuation (Gemini "leave the chat, we'll notify"), cloud autonomous (Cursor Cloud Agents, Manus Cloud Computer, Devin), durable (Dust Temporal workflows).

The pattern is *not* "agent runs code" — it is the *user experience layer* over that execution, including how the agent's actions are made inspectable, interruptible, and reversible.

## 2. Why It Matters (with academic evidence)

**Amershi et al. 2019 HAX guidelines** — the most-cited industry HAX framework — directly motivates execution UX. Specifically: G3 "Time services based on context"; G7 "Support efficient invocation"; G8 "Support efficient dismissal/interruption"; G9 "Support efficient correction"; G10 "Scope services when uncertain"; G11 "Make clear why the system did what it did"; G16 "Convey the consequences of user actions." Every execution-UX decision (plan checkpoint, runtime visibility, approval gate, artefact rendering) maps to one or more of these guidelines. [Source: academic/human-ai-interaction.md §4 — Amershi et al. 2019, doi:10.1145/3290605.3300233]

**Explainable AI (XAI)** — execution UX is the user-facing realisation of XAI's *transparency* and *explainability* principles. Rudin (2019) and Doshi-Velez & Kim (2017) argue for inherently interpretable systems; in the agent context, this translates to "every tool call should be visible to the user" — the OpenHands event-stream and LangGraph state inspection are direct realisations of this principle. [Source: academic/explainable-ai.md §2, §3 — Rudin 2019; Doshi-Velez & Kim 2017; https://en.wikipedia.org/wiki/Explainable_artificial_intelligence]

**Trust calibration** (Lee & See 2004): execution UX is the surface where trust is *calibrated*. If the agent's runtime is opaque (Cursor's "no 'why did the agent do X' introspection panel documented" [evidence/cursor.md §22]), the user cannot calibrate trust and falls into either misuse (over-trust, follows wrong actions) or disuse (under-trust, ignores correct actions). Parasuraman & Riley (1997) automation taxonomy: misuse / disuse / abuse. [Source: academic/trust-in-ai.md §3, §4 — Lee & See 2004; Parasuraman & Riley 1997]

**False trust finding** (Palod et al. 2026, arXiv:2605.10930): "Reasoning traces and post-hoc explanations are 'persuasive but not informative' — they increase user acceptance regardless of correctness. Only **contrastive dual explanations** (arguments for AND against the AI's answer) genuinely improve users' ability to distinguish correct from incorrect AI outputs." Implication: execution UX that surfaces only the agent's chosen path (most products) engenders false trust; execution UX that surfaces *alternatives considered* (LangGraph's conditional-edge visualisation, Manus's plan-vs-edit affordance) is the corrective. [Source: academic/trust-in-ai.md §4 — Palod et al. 2026; academic/progressive-disclosure.md §7]

**Cognitive Load Theory** (Sweller 1988): execution UX carries the heaviest extraneous load of any AI-UX surface because the agent's actions are typically many, fast, and complex. Without chunking (Miller's Law 7±2), the user cannot hold the agent's reasoning in working memory. Lovable's collapsed activity cards, LangGraph's turn → node → key slider, and Dust's per-message "Completed in N sec" panel are CLT-grounded chunking mitigations. [Source: academic/cognitive-load-theory.md §4, §6, §7 — Sweller 1988; chunking ~4 working-memory chunks]

**Progressive Disclosure** (Nielsen 2006; Springer & Whittaker 2018, arXiv:1811.02164): execution UX must reveal depth progressively — plan summary → activity card → step detail → tool call. Springer & Whittaker's finding that "Initially *simplified* feedback that hides potential AI errors and helps users build working heuristics > always-on full transparency" supports collapsed-by-default activity cards (Lovable, Bolt) and editable plan checkpoints (Cursor, Manus, Lovable, Bolt, Gemini). [Source: academic/progressive-disclosure.md §3, §7]

## 3. Evidence Across Products

### Gemini (Deep Research — async multi-minute execution)
Deep Research is Gemini's flagship "long execution" surface. Multi-stage agent loop:
- **Plan**: "Gemini will create a research plan for your topic."
- **Human-in-the-loop checkpoint**: "To update the research plan before you create a report, click Edit plan."
- **Execute**: "Click Start research."
- **Duration**: "It usually takes about 5-10 minutes to generate the report since Gemini analyzes many sources. For more complex reports, it may take longer."
- **Async continuation**: "While you wait for the report, you can leave the chat. When it's ready, Gemini will notify you." (web app: chat thread; mobile: device notification, including on lock screen).
- **Visuals** (Google AI Ultra plan): "Deep Research reports can include animations and visuals. These visuals help illustrate complex data and research findings... Charts, Diagrams, Interactive simulators."
- **Limits**: explicit "Daily research requests", "Number of research requests you can run at the same time". Pro/Ultra users get higher limits; near-limit a notification tells the user how many remain.
[Source: evidence/gemini.md §12, citing https://support.google.com/gemini/answer/15719111, accessed 2026-08-07]
- **Explainability affordance**: Edit Plan checkpoint is "the single strongest explainability affordance: before Gemini commits to a multi-minute browsing/analysis run, it shows the user the plan it generated, which the user can edit." [evidence/gemini.md §22]

### Manus (live runtime motion + 3 execution environments)
- **Sandbox execution**: "It operates in a complete sandbox environment—a virtual computer with internet access, a persistent file system, and the ability to install software and create custom tools." [evidence/manus.md §12, citing https://manus.im/docs/introduction/welcome]
- **Cloud Computer execution** (Apr 30 2026): always-on cloud machine. Hosted databases (MySQL), self-hosted open-source tools (Home Assistant, Metabase), scheduled scrapers. "A Cloud Computer gives you two things your laptop can't: It never turns off … Your files and setup stay put. Every regular Manus chat starts from a blank slate—it has no access to what you did yesterday. A Cloud Computer works more like your own laptop."
- **Desktop (My Computer) execution** (Mar 16 2026): local CLI. "Manus can use any tool that is accessible from your computer's command line (CLI). This includes programming languages (Python, Node.js), compilers (Swift, Xcode), and any other CLI-based applications you have installed." GPU access: "You can have Manus use your local GPU to train a machine learning model or run a large language model for inference."
- **Per-stage runtime motion**: Plan Mode explicitly breaks execution into stages. "It's natural to work in stages. Let Manus finish phase one, then turn on Plan Mode to scope phase two before it begins." [evidence/manus.md §12, citing https://manus.im/blog/manus-plan-mode]
- **Plan-then-execute lifecycle**: (1) User prompt → (2) Plan Mode evaluates and asks clarifying questions or generates Markdown plan → (3) User reviews / edits / confirms → (4) Manus executes per plan → (5) Plan can be re-opened mid-task. "Manus will not start building until you confirm or dismiss the plan. This prevents any unintended changes to your website, slides, or video." [evidence/manus.md §8]
- **Three browser surfaces, each with distinct agent affordances**: Cloud Browser (default), Browser Operator (local, Nov 18 2025), Take Over flow (Cloud Browser — when Manus encounters SMS codes, CAPTCHA, MFA: (1) Manus encounters a verification challenge; (2) You receive a notification to take over; (3) You complete the verification; (4) You hand control back to Manus; (5) Manus continues the task). [evidence/manus.md §8]
- **Live runtime motion is the agent's UX**: "You see everything Manus is doing in real-time" — Cloud Browser screenshots show live navigation, Cloud Computer shows live processes, Desktop shows live terminal output, Browser Operator shows live tab activity. [evidence/manus.md §8]
- **Scheduled task execution**: Time-triggered. Daily/weekly/monthly/custom/one-time. **Daemon pattern**: "My Computer also integrates with your personal Projects, Agents, and Scheduled Tasks. This allows you to create recurring local routines, such as tidying your Downloads folder every morning or generating a weekly summary report from your local data." **24/7 assistant pattern**: "Turn an always-on computer, into a dedicated AI assistant. You can assign it complex tasks from any of your devices, anywhere in the world, and it will work on them using its local resources." **Fire-and-forget task delegation**. [evidence/manus.md §12]

### Claude Code (CLI execution model)
- **Bash tool** — primary execution. `--allowedTools "Bash(git *)"` shows scoped Bash. Edit tool for file editing. Plan mode: `--permission-mode plan`. [evidence/claude-code.md §12, observed: `claude --help`, 2025-08-07]
- **Hooks**: lifecycle event triggers. "Hooks run your script, HTTP request, prompt, or subagent when Claude Code reaches a lifecycle event." PreToolUse, PostToolUse, etc. [evidence/claude-code.md §12, citing https://docs.anthropic.com/en/docs/claude-code/features-overview]
- **Bare mode** (`--bare`): skips hooks, LSP, plugin sync, attribution, auto-memory, background prefetches, keychain reads, and CLAUDE.md auto-discovery. [observed]
- **Background agents** (`--bg`): runs session in background. **Cloud agents** (`--cloud [description|session_id|url]`). **Custom agents** (`--agents <json>` defines custom agents at launch). **Agent teams** (experimental — "Coordinate multiple independent Claude Code sessions with shared tasks and peer-to-peer messaging"). **Ultrareview**: "Run a cloud-hosted multi-agent code review of the current branch (or a PR number / base branch) and print the findings."
- **Worktrees** (`--worktree [name]`) creates a new git worktree for the session. **Tmux** (`--tmux`) creates a tmux session for the worktree (iTerm2 native panes when available). [evidence/claude-code.md §12, §8]
- **Permission modes**: acceptEdits, auto, bypassPermissions, manual, dontAsk, plan. **Tool restriction**: `--tools "Bash,Edit,Read"` or `--tools ""` (disable all) or `--tools "default"` (all). **Tool filtering**: `--allowedTools "Bash(git *) Edit"` and `--disallowedTools` for deny-listing. **Effort levels**: low, medium, high, xhigh, max via `--effort <level>`. [evidence/claude-code.md §8]
- **Agent display in terminal**: text-based rendering. `--ax-screen-reader` for "flat text, no decorative borders or animations."
- **Explainability**: `/context` shows what's loaded; `/memory` shows what auto-memory has saved; tool calls visible in terminal output; `--verbose`; `-d, --debug [filter]` with category filtering. "No 'why did the agent do X' introspection panel documented (terminal-based, no GUI)." [evidence/claude-code.md §22]

### Codex (TUI agent loop + sandbox modes)
- **Shell tool** for command execution. **Plan tool** for planning. **Web search tool** via Responses API. **MCP servers** for external tools (GitHub, Slack, Linear per docs nav). [evidence/codex.md §12, citing agent-loop blog and security docs]
- **Sandbox modes**: read-only, workspace-write, danger-full-access. **Approval modes**: Auto (preset), Read-only, untrusted, never, on-request. `--approve-for-me` routes approval requests through automatic review using the workspace-write sandbox. `--dangerously-bypass-approvals-and-sandbox` (alias: `--yolo`). `--dangerously-bypass-hook-trust`.
- **Config override**: `-c, --config <key=value>` overrides any value from `~/.codex/config.toml`. **Feature flags**: `--enable <FEATURE>` / `--disable <FEATURE>`. **Profiles**: `-p, --profile <CONFIG_PROFILE_V2>` layers `$CODEX_HOME/<name>.config.toml` on top of base user config. **Codex SDK**: "Embed the same agent that powers the Codex CLI into your own workflows, tools, and apps." **GitHub Action**: Codex ships a GitHub Action.
- **Agent loop**: "No separate 'Agent' panel — the TUI conversation IS the agent." Default tools: Codex's default shell tool, plan tool, web search tool. Tool calls visible in the conversation transcript. `/status` shows active model, approval policy, writable roots, current token usage. `/diff` shows what changed. `/review` for code review. **Multiple agents**: Cloud supports parallel agents in different environments. `codex exec` for non-interactive runs. `codex review` for code review. **MCP server**: `codex mcp-server` starts Codex as an MCP server (stdio). [evidence/codex.md §8]
- **Explainability**: audit log `~/.codex/log/codex-tui.log` (or session-*.jsonl). Per-event OTEL categories: `codex.conversation_starts`, `codex.api_request`, `codex.sse_event`, `codex.user_prompt` (length; content redacted unless enabled), `codex.tool_*`. "No 'why did the agent do X' introspection panel documented." [evidence/codex.md §22]

### OpenHands (event-stream + TaskToolSet sub-agents)
- Tools execute via the Tool Executor, producing `ActionEvent` → `ObservationEvent` pairs. Built-in tools include TerminalTool (bash), FileEditorTool (with ApplyPatchTool as alternative for GPT-5), and custom tools. Tool calls can be executed concurrently via `tool_concurrency_limit`. Interactive Terminal guide describes agent interaction with ipython / python REPL / other interactive CLIs. [evidence/openhands.md §12, citing https://docs.openhands.dev/sdk/guides/agent-interactive-terminal.md]
- **Event-Stream Architecture (Appendix-Only Log)**: "The **Event System** provides an immutable, type-safe event framework that drives agent execution and state management. Events form an append-only log that serves as both the agent's memory and the integration point for auxiliary services." Four core responsibilities: Type Safety (Pydantic), LLM Integration, Append-Only Log, Service Integration. Event types: MessageEvent, ActionEvent (tool call with thought, reasoning, security risk), ObservationEvent, UserRejectObservation, AgentErrorEvent, SystemPromptEvent, CondensationSummaryEvent, etc. Events split into LLM-Convertible Events (visible to the LLM) and Internal Events (NOT visible to the LLM). [evidence/openhands.md §8]
- **Reasoning-Action Loop (Stateless)**: single-step execution model where each `step()` call processes one reasoning cycle. Steps: Pending Actions → Condensation → LLM Query → Response Parsing → Confirmation Check → Action Execution. Key characteristics: Stateless, Event-Driven, Interruptible (each step is atomic and can be paused/resumed). [evidence/openhands.md §8]
- **AgentDelegateAction → TaskToolSet** (V1): "lets a parent agent launch sub-agents that handle complex, multi-step tasks autonomously. Each sub-agent runs **synchronously** — the parent blocks until the sub-agent finishes and returns its result. Sub-agents can be **resumed** later using a task ID, preserving their full conversation context." Parallel delegation supported via `tool_concurrency_limit` (default 1; 2-8 moderate; >8 high parallelism). Verbatim: "the main agent has `tool_concurrency_limit=8`, allowing it to delegate to all three sub-agents simultaneously" + "Do NOT delegate one at a time - call all three delegate tools in a single response." File-Based Agents (Markdown files with YAML frontmatter). **ACP Agent** (Agent-Client Protocol): "Delegate to an ACP-compatible server (Claude Code, Gemini CLI, etc.) instead of calling an LLM directly." [evidence/openhands.md §8]
- **Explainability**: architectural rather than operational. Every ActionEvent captures thought + reasoning + security risk. Every ObservationEvent captures the tool execution result. Append-only event log is canonical trace. **Observability & Tracing** via OpenTelemetry. **Metrics Tracking** — token usage, costs, latency. **Critic (Experimental)** — real-time evaluation of agent actions using an LLM-based critic model. "This is a stark contrast to Continue (no published trace) and Replit (operational work-log + video replay)." [evidence/openhands.md §22]

### LangGraph Studio (animated graph traversal + time travel)
- A run flows: client → API server creates pending run in durable task queue → queue worker acquires lease, loads graph, executes; queue enforces at most 1 concurrent run per thread. Each super-step writes a checkpoint (durability mode `async` writes after each step; `exit` only the final state). Default `--n-jobs-per-worker` is 10 (configurable via CLI flag). Latency per node depends on the underlying LLM call / tool execution; Studio shows per-node timings inline (token/latency metrics from LangSmith integration). Each LLM call inside a node can be opened in the Playground from the "View LLM Runs" affordance — without rerunning the graph. [evidence/langgraph-studio.md §12]
- **Animated graph traversal**: Studio renders the compiled graph as a static diagram, and during a run the active node is visually highlighted as the graph's execution pointer traverses the edges in real time. The slider at the top of the page controls the "super-step" granularity visible in the thread log; dragging it right exposes more granular detail (turns / nodes / state keys), dragging left collapses. Each node, when clicked, opens an **Inspect** panel showing its input state, output state, and any LLM/tool calls. "Crucially the agent graph is itself the navigation surface — you don't scroll a list of traces, you watch the agent *move* through its decision space." Streaming events are forwarded by the queue worker over SSE. Conditional edges during animation show as branch candidates so the developer can see *which* path was chosen and why. [evidence/langgraph-studio.md §8]
- **Explainability — crown jewel**: Every checkpoint stores the full graph state after each super-step. The `get_state_history(config)` API returns this history in reverse chronological order, so the developer can replay or fork from any point. **Replay** re-executes nodes from a prior checkpoint — "Replay re-executes nodes—it doesn't just read from cache. LLM calls, API requests, and interrupts fire again and may return different results." **Fork** creates a new branch with modified state via `update_state` — "update_state does not roll back a thread. It creates a new checkpoint that branches from the specified point. The original execution history remains intact." **Subgraph time travel**: by default subgraphs inherit the parent's checkpointer; setting `checkpointer=True` on the subgraph gives it its own checkpoint history. Interrupts (HITL) are always re-triggered during time travel so human-in-the-loop flows replay correctly. In the UI: clicking **Edit node state** opens the JSON editor; clicking **Fork** creates a new forked run; clicking **Re-run from here** creates a new forked run without state edits. Per-node LLM calls can be opened in Playground with the full prompt context. [evidence/langgraph-studio.md §22]

### Dust (deep-dive agent runs + Temporal durability)
- Agent execution model: user sends message → agent reasoning + tool calls + skills activation; "the agent will decide to enable a skill by analyzing the current situation. Skills that are not relevant will not be loaded, optimizing the context exposed to the agent at a given time." **Sub-agent parallelism** (deep-dive): up to 6 concurrent @dust-task sub-agents, each with its own fresh context window. **Temporal durability**: "The system is built on Temporal workflows for durability, meaning work can survive deployments and infrastructure issues without losing progress." Latency buckets: simple questions under a minute; deep dive planning 30s–2min; research phase 5–20min; synthesis 1–3min. **Tool output pruning** ("Big Loop" + "Amnesia" prevention): "selectively prune tool outputs by replacing their content with `<dust_system>This tool output is no longer available</dust_system>`. The tool call itself remains visible, so the model still sees what it did, just not the full results." **Offloaded tool use**: large tool outputs are stored as files with snippets inline + full filesystem access for retrieval (offset, limit, regex, semantic search). **Long-running durable agents** shipped as a feature (Sep 2025 changelog). [evidence/dust.md §12]
- **Steering**: every step (thinking blocks, tool calls, searches, file operations) appears live as it happens. "Every step now appears live in the conversation... instead of hiding behind a single activity indicator." Users can send messages mid-run; the agent finishes its current round of parallel actions then picks up the queued message with full context. Stop button keeps all completed work — "everything it's already done is kept. You only stop what comes next." [evidence/dust.md §8]
- **Workspace-level Agent Builder Observability**: "Builder Observability lets you see exactly where they're crushing it (and where they're not)... which tools your agents use, when they use them, and how behavior shifts between versions. It allows you to see real usage patterns, identify bottlenecks, and iterate based on real behavior." Per-agent observability materialised in Workspace Analytics: "Agents by credits: the top 100 agents by credits consumed, with their model, description, top users, and top skills... Skill usage: executions and unique users per skill over time... Tool usage: executions and unique users per tool over time." "This is genuinely differentiated — most agent platforms surface traces; Dust surfaces *aggregate agent behaviour* (which skills fired, which users, which tools, model drift over versions)." [evidence/dust.md §8]

### Lovable (Build mode + Try-to-fix + visible steps)
- Build mode executes "end to end" with these visible steps: current step being executed, files being modified, tools being used (search, web fetch, image generation), progress through multi-step implementations. Available tools include browser testing (real browser in virtual environment, "clicking buttons, filling forms, testing flows, and checking behavior across screen sizes"), frontend tests, edge function verification. Build errors trigger a **Try to fix** button on the activity card — "Fixing errors is free within our fair use policy" — but if used heavily, further fixes run as normal chat messages and are charged. There is no user-visible terminal/HMR in Lovable (preview is server-rendered cloud-side, not a WebContainer), so the user sees only the live preview updating. Stop button halts the current task; stopped requests are charged based on work completed. [evidence/lovable.md §12, citing https://docs.lovable.dev/features/agent-mode.md]
- **Explainability**: Activity cards per action (file edits, commands, web searches, browser tests, subagent delegations) are expandable to inspect details. After response, action summary + "what changed" is provided. Each version in history shows **View code changes** (diff of files/lines changed) and **Go to message in chat** (jump to conversation moment that produced the version). Per-message cost shown in "Credits used" in More options menu. Plan mode creates a structured plan document (high-level overview, key decisions/assumptions/constraints, components/data models/APIs, step-by-step sequencing, optional diagrams) that is "fully editable as markdown before approval". Subagents return findings to main agent (read-only) — visible to user via activity card. [evidence/lovable.md §22]

### Bolt (WebContainer in-browser execution)
- Bolt executes locally in-browser via **WebContainers** — "the technology that first made it possible to run Node.js directly in your browser." Capabilities: "Run the native versions of `npm`, `pnpm`, and `yarn`, all in the browser, all in your app, up to 10x faster than local"; "Full browser support: Run WebContainer in all major browsers, from Chromium-based, to Firefox or Safari TP"; "All major frameworks: Instantly spin up disposable environments running any major modern framework"; "Run Wasm out of the box".
- **Boot sequence**: `WebContainer.boot()` → mount files → `npm i` → `npm run dev` (dev server in-browser).
- **HMR**: After saving in Code view (`Ctrl+S`), "Bolt automatically builds your changes" — Code view → Preview toggle to see results.
- **Project lifecycle**: Design/plan → first prompt → iterate → publish (Bolt hosting / Netlify / GitHub / Expo / Download).
- **Mobile app builds via Expo** — "Using Bolt with Expo to create mobile apps and publish them to app stores".
- **No documented user-facing terminal in the Bolt editor** (terminal exists in StackBlitz IDE for projects pre-April-2026 storage format, when "Open in StackBlitz" was available). **Evidence gap**: explicit terminal/HMR-panel UX in current Bolt editor not documented.
[evidence/bolt.md §12, citing https://webcontainer.io, accessed 2026-08-07]
- **Explainability**: Version history is the primary explainability artifact. Backup name change; Bookmark feature. Token display in chat (opt-in). Plan Mode provides structured plans + "Implement this plan" / "Show an example" / "Refine this idea" action buttons. Plan Mode web research: "When Bolt answers a question, it can pull in real-time, up-to-date information from trusted web sources instead of just relying on what it was trained on. When a search has been conducted, Bolt displays the sources at the top of the response". Inspector tool: "Use the Inspector tool to highlight a component within a page, and discuss potential changes" — visible targeting during Plan mode. **Evidence gap**: Bolt does NOT publish a per-message cost breakdown like Lovable's "Credits used" menu — token consumption is shown only as a balance decrement. [evidence/bolt.md §22]

### v0 (Vercel Sandbox Firecracker microVM + work details)
- **Generation loop**: v0 generates code → runs in Vercel Sandbox dev server → renders live preview → if errors, automatic error fixing kicks in → on completion, user reviews version.
- **Sandbox = Vercel Sandbox (Firecracker microVM)**: "VM-backed chats run your project inside an isolated Vercel Sandbox that hosts your code, dev server, terminal, and agent tools." Replaces older browser-based preview.
- **Isolation boundaries**: Per chat (each VM-backed chat has its own sandbox; files/env/running processes never cross); per user or team (others can't reach unless shared); from production (sandbox never same machine as deployed app).
- **Sandbox lifecycle**: Created first time chat needs one; 30-minute pooled lifetime initial timeout; active running sandboxes auto-extend +10 min when ≤5 min remaining; **24-hour absolute cap**; inactive/stopped sandboxes NOT revived by keep-alive (reused or recreated on next visit); new VM-backed chat creates new sandbox; "State doesn't carry over from older chats unless you explicitly fork or import."
- **Sandbox network policy**: "Sandbox Network Policy controls which outbound hosts the sandbox is allowed to reach. The default is allow-all. Team owners configure this from team settings."
- **What runs inside**: Node.js with pnpm/npm/yarn/bun; framework-aware dev server (Next.js, Vite, generic Node.js); environment variables from connected Vercel project.
- **Performance**: "Sandboxes start over 50% faster on new chats and use about 500 MB less storage" (May 12 2026). "Faster VM preview startup and Vercel deploys, trimming several seconds of setup" (Jul 7, 2026). "Preview sandboxes can run for up to 24 hours." Preview sandboxes limit: "Signed-out users get a higher preview sandbox limit of 240 per hour, and hitting it prompts sign up or sign in."
[evidence/v0.md §12, citing https://v0.dev/docs/sandbox + https://v0.dev/changelog, accessed 2026-08-07]

## 4. Observed Variations

Seven distinct execution-UX variations observed across the 11 products:

1. **CLI/TUI execution** (Claude Code, Codex) — terminal-native; no GUI; tool calls visible in transcript; slash commands for status/diff/review; `--bg` for async background; debug flags for category-filtered logging.
2. **Synchronous chat-loop execution** (Cursor, Lovable, Bolt, v0) — agent runs in foreground; user sees activity cards / streaming parts / live preview; Stop button halts; completion → user reviews version.
3. **Async multi-minute execution** (Gemini Deep Research) — explicit plan checkpoint, 5-10 min runtime, async continuation with notification, no live streaming required.
4. **Live runtime motion execution** (Manus) — three environments (Sandbox / Desktop / Cloud Computer), each with a live pane showing the agent's actions (browser navigation, terminal output, browser operator activity). Plan Mode breaks execution into stages.
5. **Event-stream execution** (OpenHands) — append-only event log; ActionEvent + ObservationEvent pairs; LLM-Convertible vs Internal event split; stateless step() loop; TaskToolSet sub-agents.
6. **Animated graph traversal execution** (LangGraph Studio) — graph as navigation surface; per-node Inspect panel; slider for super-step granularity; time-travel via checkpoint history; Fork creates new branch without rollback.
7. **Durable workflow execution** (Dust) — Temporal workflows; up to 6 concurrent @dust-task sub-agents; tool output pruning ("Amnesia" prevention); offloaded tool use (file storage + snippet inline); long-running durable agents.

An eighth hybrid — **autonomous cloud execution** (Cursor Cloud Agents, Manus Cloud Computer, Devin Managed Devins, GitHub Copilot Cloud Agent) — runs in a cloud VM; user may close the client; results delivered via dashboard/PR/Slack.

A ninth — **in-browser execution** (Bolt WebContainers) — runs Node.js locally in the browser; no server round-trip for execution; 10x faster than local for npm/pnpm/yarn.

## 5. Premium Exemplars (which do it BEST and WHY — evidence-based)

**LangGraph Studio — best execution UX for developer observability.** Verdict: best for *observability* because (a) the agent graph is itself the navigation surface — "you don't scroll a list of traces, you watch the agent *move* through its decision space" [evidence/langgraph-studio.md §8]; (b) time-travel via checkpoint history allows replay AND fork — "Replay re-executes nodes—it doesn't just read from cache. ## 6. Anti-Patterns (which FAIL and WHY — evidence-based)

**Cursor's missing introspection panel.** Anti-pattern: "No 'why did the agent do X' introspection panel documented" [evidence/cursor.md §22]. Cursor's Plan Mode is the only explainability affordance; once execution begins, the user cannot ask "why did you do that?" mid-run. This violates Amershi et al. 2019 G11 ("Make clear why the system did what it did") [academic/human-ai-interaction.md §4] and risks Palod et al. 2026's false-trust failure mode — users accept agent actions without verifying [academic/trust-in-ai.md §4].

**Codex's `--yolo` flag as documented escape hatch.** Anti-pattern: `--dangerously-bypass-approvals-and-sandbox` (alias: `--yolo`) is documented [evidence/codex.md §12, citing security docs]. Documenting a "yolo" flag invites misuse — Parasuraman & Riley (1997) automation abuse category [academic/trust-in-ai.md §4]. While sandbox modes are progressive (read-only → workspace-write → danger-full-access), the existence of a documented `--yolo` shortcut normalises the most dangerous mode.

**Claude Code's terminal-only rendering excludes GUI users.** Anti-pattern: "Agent display in terminal: text-based rendering. `--ax-screen-reader` for 'flat text, no decorative borders or animations.'" [evidence/claude-code.md §8]. "No 'why did the agent do X' introspection panel documented (terminal-based, no GUI)" [evidence/claude-code.md §22]. The CLI execution UX is power-user-optimised; users without terminal fluency cannot effectively monitor long-running agent execution. Accessibility: `--ax-screen-reader` is a positive affordance for screen-reader users but the broader UX assumes terminal literacy.

**Gemini's mode + model + source conflation.** Anti-pattern: "Gemini's primary progressive disclosure failure mode is the **mode + model + source conflation in the same text box**" — "Add Files" exposes Files upload, Image upload, Deep Research, Canvas (four very different feature modes behind one button); "Sources" within Deep Research exposes Google Search, Gmail, Drive, NotebookLM (collapsing source selection); "Pro" vs "Thinking" model selection reached via secondary flow; "@app" mention syntax adds Connected Apps into the prompt box, making app invocation implicit. "This is a textbook **overload example**: one text box, four orthogonal toggles (mode, source, model, connected app). New users cannot infer from the surface what each affordance does." [evidence/gemini.md §18]. This violates CLT redundancy effect (academic/cognitive-load-theory.md §6) — the four axes are conceptually duplicative.

**Bolt's missing per-message cost breakdown.** Anti-pattern: "Bolt does NOT publish a per-message cost breakdown like Lovable's 'Credits used' menu — token consumption is shown only as a balance decrement (e.g., '96K → 26K = 70K used'), not as a per-action accounting." [evidence/bolt.md §22 — evidence gap]. Without per-action cost visibility, the user cannot calibrate which operations are expensive — violating trust-calibration principles (Lee & See 2004; academic/trust-in-ai.md §3).

**Cursor evidence reliance on RSC payload + forum.** Observation: multiple Cursor execution-UX claims cite "https://cursor.com/docs/agent (RSC payload)" or "https://forum.cursor.com/t/understanding-cursors-ai-feature/7204" [evidence/cursor.md §8, §12, §14]. RSC (React Server Components) payloads are JSON, not human-readable docs; forum posts are community-sourced, not official. This is an evidence-quality concern rather than an execution-UX anti-pattern, but it limits confidence in Cursor-specific execution-UX claims.

**Bolt's missing terminal/HMR-panel UX documentation.** Evidence gap: "explicit terminal/HMR-panel UX in current Bolt editor not documented" [evidence/bolt.md §12]. Bolt's WebContainer execution model is documented but the user-visible surface of that execution (is there a terminal panel? an HMR indicator? a build-log stream?) is not. This is a documentation gap that propagates into a UX gap for users trying to debug build failures.

**Manus per-command approval fatigue.** Anti-pattern: "Per-command approval fatigue is the core trust cost: Every Desktop terminal command prompts Allow Once / Always Allow" [evidence/manus.md §8, citing https://manus.im/docs/features/desktop]. While approval gates are good (Amershi et al. G16 "Convey the consequences of user actions"), per-command approval fatigue leads to either (a) user disengagement (clicking "Always Allow" without reading) or (b) abandonment of the Desktop mode entirely. This is the *over-correction* of trust calibration — Parasuraman & Riley's "disuse" failure mode.

## 7. Cognitive Load Implications (cite CLT)

**CLT source**: Sweller (1988); Sweller, Ayres & Kalyuga (2011); Chandler & Sweller (1991). [Source: academic/cognitive-load-theory.md §2, §4]

**Intrinsic load (IL)** in execution UX is determined by (a) the *number of tool calls per agent run* (more calls → more IL to track), (b) the *duration of the run* (longer runs → more working-memory decay; user forgets the original prompt), (c) the *complexity of the agent's reasoning chain* (multi-step plans > single-shot completions). Manus's per-stage Plan Mode explicitly mitigates (b): "It's natural to work in stages. Let Manus finish phase one, then turn on Plan Mode to scope phase two before it begins" [evidence/manus.md §12].

**Extraneous load (EL)** in execution UX comes from:
- **Choice overload** in Gemini's mode + model + source conflation (§6 anti-pattern) — pure EL.
- **Hidden runtime** when execution is opaque (Cursor no introspection panel — §6 anti-pattern) — the user mentally simulates the agent's actions, incurring EL.
- **Multi-agent state tracking** — Dust's 6 concurrent sub-agents each with their own context window [evidence/dust.md §12] require the user to track 6 separate streams. Mitigated by Dust's per-agent Workspace Analytics aggregation.
- **Long activity logs** — Lovable's expandable activity cards collapse by default (PD), reducing EL; users expand only what they need to inspect.
- **Streamed progress without structure** — Gemini Deep Research's streaming (5-10 min) without structured intermediate disclosure could be high-EL; mitigated by Edit Plan checkpoint before execution begins.

**Germane load (GL)** is maximised when execution UX surfaces *structure*:
- LangGraph Studio's graph-as-navigation surface teaches the user the agent's decision space — over time the user builds a schema of the graph topology.
- OpenHands's event-stream teaches the user the agent's reasoning chain — each ActionEvent captures thought + reasoning + security risk; over time the user internalises the action vocabulary.
- Manus's plan-then-execute lifecycle teaches the user what the agent will do before it does it — schema construction before observation.
- v0's API streaming parts (text, thinking, file reads and edits, searches, bash commands, tool calls, agent actions) provide explicit chunking that aids schema construction.

**Expertise-reversal effect** (Kalyuga 2011; academic/cognitive-load-theory.md §4): expert developers benefit from CLI/TUI (Claude Code, Codex) because they can read tool-call transcripts natively; novice developers benefit from GUI execution UX (Lovable activity cards, v0 tool-execution cards, Manus live panes). The 11 studied products span this expertise spectrum — CLI tools (Claude Code, Codex) target experts; GUI tools (Lovable, Bolt, v0) target novices; hybrid tools (Cursor, Manus) span both.

**Chunking (Miller's Law 7±2)**: Lovable's activity cards are one chunk per action; LangGraph's turn → node → key slider lets the user choose chunk granularity; Dust's per-message "Completed in N sec" detail panel is a single-chunk summary that expands to per-step detail. All three are CLT-grounded chunking patterns. [academic/cognitive-load-theory.md §6 — "Chunking content: respects working memory limit (~4 chunks)"]

**Modality effect** (Mousavi et al.; academic/cognitive-load-theory.md §6): Manus's multi-pane live motion (browser pane + terminal pane + plan pane) uses visual + textual modality simultaneously — research suggests this reduces EL vs. text-only.

## 8. Progressive Disclosure Relationship

**Academic grounding**: Nielsen (2006) PD criteria + Springer & Whittaker (2018, arXiv:1811.02164) on AI transparency. [Source: academic/progressive-disclosure.md §3, §4, §7]

**Manus Skills Progressive Disclosure (explicitly named)**: "Skills are designed to be highly efficient by using a 'Progressive Disclosure' mechanism. This ensures that the agent only loads the information it needs, when it needs it, preserving the valuable context window." Three levels:
- Level 1: Metadata (name + description) — loaded at startup — ~100 tokens/Skill
- Level 2: Instructions (SKILL.md content) — loaded when triggered via slash command — <5k tokens
- Level 3: Resources (scripts, reference files) — loaded on demand when referenced — consumed only when used
[evidence/manus.md §18, citing https://manus.im/docs/features/skills]

**Cursor layered reveal**: User starts with Cmd-K (simplest). Cmd-L chat is one level up. Cmd-I Composer is multi-file. Plan Mode is full-agent. Cloud Agents are remote autonomous. [evidence/cursor.md §18, citing forum + blog]

**Claude Code layered extensions** in recommended order: (1) CLAUDE.md (always-on context); (2) Skills (on-demand invocable); (3) Code intelligence plugin (always-on LSP); (4) MCP (external services); (5) Subagents (isolated workers); (6) Agent teams (multi-session coordination, experimental); (7) Hooks (event automation); (8) Plugins (packaging + distribution). "Build your setup over time: You don't need to configure everything up front." Triggers listed (e.g., "Claude gets a convention or command wrong twice → Add it to CLAUDE.md"). Safe mode strips all customizations. Bare mode strips LSP, hooks, plugins, attribution, auto-memory, prefetches, keychain, CLAUDE.md auto-discovery. [evidence/claude-code.md §18]

**Codex progressive disclosure**: On launch, Codex detects whether the folder is version-controlled and recommends: version-controlled folders: Auto (workspace write + on-request approvals); non-version-controlled folders: read-only. Slash commands as progressive disclosure. Approval modes from strict to loose: read-only → untrusted → on-request → never. Configuration layering: `~/.codex/config.toml` (base) → `<name>.config.toml` (profile) → `-c` overrides (CLI). Feature flags for experimental features. [evidence/codex.md §18]

**LangGraph Studio layered**: Thread log: **turn → node → key**, all collapse/expand. Slider sets the global expansion threshold. Pretty vs JSON mode is a per-step toggle. Per-node: clicking a node shows its state diff; clicking **View LLM Runs** opens the LLM call list; clicking an LLM call opens it in Playground. Playground itself is a sub-UI that lets you iterate on a single prompt without rerunning the graph. The **Edit node state** modal opens JSON editor; **Fork** is the destructive-but-safe action. "This layering — Overview → Node → LLM call → Prompt — is the canonical LangGraph progressive-disclosure stack." [evidence/langgraph-studio.md §18]

**Dust layered**: (1) conversation message → (2) "Completed in N sec" details panel → (3) per-step tool call inspection → (4) skill usage summary at the bottom. Agent Builder: top-level tabs → per-tab advanced sub-sections (e.g., "Advanced settings" inside Knowledge search enables Advanced search mode). Skills dynamically load: "the skill loads dynamically, keeping the context lighter for the agent when not needed, making it more focused and less prone to hallucinations." [evidence/dust.md §18]

**Lovable strong PD pattern**: Activity cards collapsed by default; expand to inspect. "More options" menu on a response reveals Copy message link / Preview / Worked time / Credits used. "More" tab in project toolbar hides Analytics, Cloud, Agent integrations, Payments, Connectors, Security, SEO & AI search, Sensitive data — "What you see in the More menu depends on your project and plan: sections tied to a feature appear once you use it". Plan view opens full screen only when there's a plan to review. Preview toolbar can be hidden completely until needed. Suggestions from Lovable appear "as clickable chips near the chat input" after a response — visible but ignorable; can be turned off in account settings. [evidence/lovable.md §18]

**v0 PD**: Docs nav groups Getting Started → Prompt → Iterate → Integrate → Ship → Manage → Guides (six-step funnel mirroring product journey). Three terminal permission modes (Ask/Auto/Full) progressively disclose autonomy. Pre-installed agents (Claude Code) disabled for Enterprise by default — opt-in progressive disclosure at the org level. Plan-tiered disclosure: Enterprise gets SAML SSO, RBAC, training opt-out, priority access, SLAs. Business gets training opt-out by default. [evidence/v0.md §18]

**Academic warning (Palod et al. 2026)**: PD must not become "opacity theatre" — users must be able to drill down to verify. Cursor's Plan Mode Markdown plan file is editable by the user — a verifiability affordance that prevents opacity theatre. LangGraph's per-node LLM call Playground opening is a similar verifiability affordance. Dust's per-message detail panel + per-agent Workspace Analytics is a verifiability affordance. By contrast, Cursor's missing introspection panel (§6 anti-pattern) is opacity theatre. [Source: academic/progressive-disclosure.md §7; academic/trust-in-ai.md §4 — Palod et al. 2026]

**Springer & Whittaker (2018, arXiv:1811.02164)** finding supports Lovable/Bolt's collapsed-by-default activity cards + Manus's Plan Mode opt-in: "Initially *simplified* feedback that hides potential AI errors and helps users build working heuristics > always-on full transparency. Incremental (continuous) transparency feedback can be distracting and undermine simple heuristics — users retract positive evaluations after experience." [academic/progressive-disclosure.md §7]

## 9. Accessibility Considerations

**Claude Code** — explicit screen-reader affordance: `--ax-screen-reader` flag for "flat text, no decorative borders or animations" [evidence/claude-code.md §8]. Users with visual impairments are poorly served by the visual-first execution-UX paradigm across all studied products except Claude Code's `--ax-screen-reader` flag. This is a significant pattern-wide accessibility gap.

## 10. Performance Implications

**Execution-UX latency buckets** (Dust's documented buckets): simple questions under a minute; deep dive planning 30s–2min; research phase 5–20min; synthesis 1–3min [evidence/dust.md §12]. These buckets define the UX latency budget for each execution type.

**Gemini Deep Research** (5-10 min runtime): mitigated by async continuation — "While you wait for the report, you can leave the chat. When it's ready, Gemini will notify you." Mobile: device notification including on lock screen. [evidence/gemini.md §12]. **Implication**: long execution requires async UX; blocking UX would fail.

**Bolt WebContainers** (10x faster than local): "Run the native versions of `npm`, `pnpm`, and `yarn`, all in the browser, all in your app, up to 10x faster than local." [evidence/bolt.md §12, citing https://webcontainer.io]. **Implication**: in-browser execution can be faster than local for npm operations, eliminating the dev-server boot cost from execution UX.

**v0 Sandbox** (50% faster startup, 500MB less storage, 24-hour cap): "Sandboxes start over 50% faster on new chats and use about 500 MB less storage" (May 2026). "Faster VM preview startup and Vercel deploys, trimming several seconds of setup" (Jul 2026). [evidence/v0.md §12]. **Implication**: Firecracker microVM is the modern standard for code-gen sandbox performance.

**Claude Code** (TUI rendering, no GUI overhead): text-based rendering is sub-frame; `--ax-screen-reader` strips animations for accessibility. Background agents (`--bg`) run without blocking the terminal. Worktrees + tmux for parallel sessions. [evidence/claude-code.md §8, §12]

**Manus Cloud Computer** (always-on, persistent file system): "A Cloud Computer gives you two things your laptop can't: It never turns off … Your files and setup stay put." [evidence/manus.md §12]. **Implication**: cloud execution removes the boot/perf cost from local execution UX; user sees only the live motion.

**Dust Temporal workflows** (durable): "work can survive deployments and infrastructure issues without losing progress" [evidence/dust.md §12]. **Implication**: execution UX must handle *resumption* — when an agent resumes after infrastructure failure, the user must see the prior state restored.

**OpenHands tool_concurrency_limit** (default 1, moderate 2-8, high >8): parallel tool execution increases throughput but raises cognitive load (§7). [evidence/openhands.md §8, §12]

**LangGraph per-node timings** (inline display): Studio shows per-node timings inline (token/latency metrics from LangSmith integration). [evidence/langgraph-studio.md §12]. **Implication**: per-node latency visibility is the developer-facing perf surface.

**Synthesised finding**: execution-UX performance perception correlates with (a) async continuation for >2min runs (Gemini, Manus Cloud Computer, Cursor Cloud Agents, Devin, Dust durable agents); (b) Firecracker microVM for code-gen sandboxes (v0); (c) WebContainer for in-browser dev servers (Bolt); (d) local-first for interactive runs (Claude Code TUI, Codex TUI).

## 11. Long-Session Impact

**Dust long-running durable agents** (Sep 2025 changelog): Temporal workflows survive deployments and infrastructure issues. Tool output pruning ("Amnesia" prevention) keeps context manageable across long sessions — "selectively prune tool outputs by replacing their content with `<dust_system>This tool output is no longer available</dust_system>`. The tool call itself remains visible, so the model still sees what it did, just not the full results." [evidence/dust.md §12]

**Manus Cloud Computer** (always-on): "Your files and setup stay put. Every regular Manus chat starts from a blank slate—it has no access to what you did yesterday. A Cloud Computer works more like your own laptop." [evidence/manus.md §12]. **Implication**: long-session execution UX benefits from persistent state across sessions; ephemeral sandboxes (v0 24-hour cap, Bolt in-browser) reset between sessions.

**v0 Sandbox 24-hour absolute cap**: inactive/stopped sandboxes NOT revived by keep-alive (reused or recreated on next visit); new VM-backed chat creates new sandbox. "State doesn't carry over from older chats unless you explicitly fork or import." [evidence/v0.md §12]. **Implication**: v0 explicitly trades long-session durability for sandbox isolation; users must explicitly fork or import to preserve state.

**Claude Code background agents** (`--bg`): runs session in background; managed with `claude agents`. Cloud agents (`--cloud [description|session_id|url]`) provide async continuation. Worktrees + tmux for parallel long-running sessions. [evidence/claude-code.md §12, §8]

**OpenHands stateless step() loop**: "Stateless (no mutable state between steps), Event-Driven (reads from event history, writes new events), Interruptible (each step is atomic and can be paused/resumed)." [evidence/openhands.md §8]. **Implication**: long sessions are inherently resumable because state is in the event log, not in memory.

**Cursor Cloud Agents**: "can build, test, and interact with the changed software. They can also use computers to control the desktop and browser." Cloud Agents dashboard shows environment, version history. [evidence/cursor.md §8, §12]

**Lovable Stop button**: halts the current task; stopped requests are charged based on work completed. [evidence/lovable.md §12]. **Implication**: long-session execution UX must have explicit stop semantics with cost-bounding.

**Gemini Deep Research daily limits**: explicit "Daily research requests", "Number of research requests you can run at the same time". Pro/Ultra users get higher limits; near-limit a notification tells the user how many remain. [evidence/gemini.md §12]. **Implication**: long-session execution UX must surface remaining quota to prevent surprise cutoffs.

**Pattern-wide observation**: long-session execution UX quality correlates with (a) durable workflow infrastructure (Dust Temporal; OpenHands event-stream), (b) cloud always-on execution (Manus Cloud Computer; Cursor Cloud Agents; Devin Managed Devins), (c) explicit session lifecycle policy (v0 24-hour cap; Lovable Stop button; Gemini daily limits). Products without explicit long-session policies risk context overflow (Dust's "Amnesia" prevention), state loss (v0 sandbox reset), or quota surprise (Gemini near-limit notification is the corrective).
